# VINTAGE ALARM — チャットプレゼン納品規約

> **CURRENT / USER-APPROVED (2026-10-15 JST)**
>
> 対象はChatGPT等の**チャット画面で提出するプレゼン**。「プレゼンして」を受けたときに発動する。PowerPoint、PDF、LP、サイト掲載用コピーの規格ではない。単一正本は本ファイル。入口は `PROJECT.md` §2。

## 1. 起動条件・優先順位

- `プレゼンして`、`チャットでプレゼン`、`プレゼン形式で納品`など、VAの調査・個体研究・動画分析・サイト紹介・比較をチャットプレゼンとして**提出する明示的な依頼**に適用する。
- 「どうプレゼンするか教えて」「プレゼンを評価して」は**方法論の相談・評価**であり、実物のプレゼンを強制生成するトリガーではない。話題に「プレゼン」という単語があるだけでは起動しない。
- 正本の取得順は `PROJECT.md` §0を厳守。個体研究はAGENTSの時計研究フレーム、WATCH本文やOWNER'S NOTEは `SITE_RULES.md`、画像やUIの現物は対象資料が優先。SNS / Councilを併用する場合は、それぞれの正本を取得して**分析のプロトコルと、プレゼンの提出様式を分離**する。
- **対象と聴衆を依頼から決める。** 「何も知らない第三者向け」なら用語を説明する。時計研究の中間報告なら、ユーザーが必要とする調査深度は落とさない。単語だけ小学生向けに変える、知識量を勝手に固定することはしない。
- **納品先は原則チャット本文。** 指示なしにスライド・PDF・画像・別サイト・Workへ移さない。写真や比較フレームの表示は、実際のソース画像を検証できる場合に限る。

## 2. 目標

**結論がすぐ分かる。それでも、読み進めるほど「なぜ？」「なるほど！」という発見があり、最後には根拠と判断を自分でも追える。**

条件:
1. **理解** — 最初の画面で何の話か、主張や暫定判断が分かる。
2. **引き込み** — 時計の意外な構造、実機写真の差、資料の食い違いなど**現実に存在する面白さ**で好奇心を作る。単なる煽り・もったいぶり・「続きは次回」は使わない。
3. **検証可能性** — 主張に対応する実物・図・数字・原典が近くにある。分かったこと／資料記載／ユーザー報告／仮説／未確認が曖昧にならない。
4. **納得と前進** — 説明や比較を経て、なぜその評価・次の調査・撮影方針になるかが分かる。
5. **完成品** — いま分かる範囲で一度読み切れる。末尾で「続きも作ろうか」と成果物を未完成扱いしない。

## 3. 構成：固定テンプレートではなく、読者の理解の順番

基本は以下の**論理の流れ**。毎回すべてを見出し化・番号化しない。

1. **冒頭**：一言の結論／今回の対象を明示する。事実の裏づけがある興味深い対比・問い・写真を置けるなら置く。
2. **現物・事件・問い**：何が実際に起きた／写っている／記録されているか。実物・資料の具体から入る。
3. **発見の展開**：ただ列挙するのではなく、**Aはこう、Bはこう → その違いは何か → 何が分かるか**。予想が変わる発見を根拠付きで提示する。
4. **反論・別解**：比較条件がそろわない、原典に異説があるなど、結論を左右する異議は隠さない。演出のためだけの架空の論争や、不要な全件監査の公開は避ける。
5. **着地点**：今回の判断、残る未確認、次の実行／検証。**調査途中の一回納品**なら、研究全体の完成とは区別して「今回到達した地点」を明確にする。
6. **出典導線**：必要な箇所へ近接して根拠を置き、最後に主要な参照先を短く示す。引用元を求められた場合は実在するURLを提示する。

「証拠 → どう読めるか → だから次は何をする」の**論理のつながり**を省かない。結論を冒頭で示した後、同じ言葉を最後まで何度も繰り返すのではなく、知識・理解が前進する構成にする。

## 4. チャット画面での見せ方

- **スマホの縦スクロールが基準**。短い冒頭、自然な段落、意味を伝える少数の見出し。装飾目的の大量カード・バッジ・絵文字・区切りを避ける。
- **事実を見せる**：実機写真・動画フレーム、該当部品の拡大、一次資料の該当箇所、測定表・グラフは、閲覧者が確認できる形でその説明のすぐ近くへ配置する。
- **意味が見える比較**：A/Bの違いが視覚的に理解しやすいなら、並列画像や小表を使う。スマホで読めない多列表を無理に使わない。
- **情報に緩急**：意外な証拠は短い一文で立ち止まらせ、技術的な仕組みや出典は必要なだけ厚く説明する。全段落を均等な長さにしない。
- **専門語は残す**：初出で意味や動きを簡潔に説明する。「小学生でも理解できる」と「幼稚に書く」は別。
- **演出素材の出所**：実物未確認の時計へ似た検索画像を紛れ込ませない。別個体・模式図・参考画像を使う場合は明示する。アクセスしていないURLを確認済みと呼ばない。画像・音を表示できないときは、確認できた内容に限定して説明する。
- 実際の音声や動画をチャットで直接再生できない場合、再生したと偽らない。確かな音源リンクがあれば提示する。使えない操作ボタンや意味のないチェックボックスは付けない。
- **チャット内の完成稿**を優先する。制作メモ、UI仕様、長い進捗ログ、採点表だけを提出物にしない。

## 5. 調査の段階納品（時計リサーチの標準的な使い方）

ユーザーは今後、時計研究を進めながら**その時点の内容を一度プレゼンとして受け取る**。調査全体の完了を待たず、明示された区切り・依頼時に読み切れる報告を提出する。

- **その回で確認したこと**：会社と背景、実物の機構・操作・音・外観、同系統との違いなど。AGENTSの標準研究フレームへ戻り、調べていない箱を埋めない。
- **今回の発見**：単なる年表やSPECの羅列にせず、資料・個体のどの差から何が見えたかをつなぐ。
- **未解決**：証拠不足、対立する専門書、真贋・製造時期などを明示。空白をもっともらしい話で埋めない。
- **今後の調査**：残る検証を重要度で整理。ただし完了した今回のプレゼンを「まだ提出していない」扱いにしない。
- 研究LedgerやWATCH本文をプレゼンのために要約改変しない。**研究の正本は研究の正本、プレゼンはその時点の表示用成果物**。ユーザーからGitHub登録・公開指示がない限り、チャット納品だけでrepository編集・公開しない。

## 6. 仕上げ前の監査

次をすべて確認してから提出する。

- **冒頭検査**：結論・対象が即座に伝わり、事実に根ざした興味が生まれるか。
- **発見検査**：読者が前段にない理解を次段で得るか。同じ主張の再包装やメニュー一覧の繰り返しになっていないか。
- **主張の鎖**：「他者／他機種はどうだった → 何が違った → だから何を試す」のような因果・判断の飛躍がないか。
- **出典検査**：画像、原典、数値、観測日時、ユーザー報告、仮説を分離し、断定の確度を守ったか。
- **表示検査**：スマホで余白・画像・文章が読みやすく、証拠と説明が近いか。不要な装飾で閲覧を妨げていないか。
- **完成検査**：依頼されたプレゼン自体がチャットにあり、判断や今後の課題まで一回で読めるか。完成を装った追加誘導をしていないか。
- **既存正本検査**：個体研究・SNS・Council・公開文面などの実体、CURRENT、ユーザー決定、規則と矛盾していないか。

## 7. 使用例（指示の意味）

- `VAとは何か、初めての人にプレゼンして` → 最初にサイトの対象を明示し、実機の**対比・音・歴史・実物調査**から発見を展開する。サイトのメニューの機械的紹介にしない。
- `CYMA動画の比較結果をプレゼンして` → **実際の映像で観察した差 → 何を説明できるか → 何は証明できないか → 試す撮影**の順に、実フレームと一緒に示す。撮影提案だけを出して分析を省かない。
- `ARSAの研究をここで一回プレゼンして` → **現段階の証拠から分かること／食い違うこと／調査が残ること**を、必要に応じて専門書・画像・表とともに提出。未確認の現物機能を確定させない。

**起点**：2026-10-15、ユーザーがチャットプレゼンの実例を評価・再改稿し、今後の時計リサーチの一区切り納品にも用いる方針を明示。規約制定は `U → U採用`、個々の構成・表現の提案はAI補助。研究のCURRENTや公開用原文の自動変更は含まない。
